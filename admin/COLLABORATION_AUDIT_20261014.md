# 专业协同与单机底座审计：A1

本次只核查源码、既有实验及公共查询接口，纠正文档，不修改实现、不启动新 EDA 优化。本审计优先于此前关于夜间 N4“真实 DPL 候选继续 CTS/route”的验收结论。O2 独立分支的指标、重放和逻辑等价结论保持。

## 最重要的更正：DPL 交接后被覆盖

`admin/overnight_dpl.py::finish` 将 DPL 的 `candidate/legalized.odb` 复制为 `3_5_place_dp.odb` / `3_place.odb`，随后以新 WORK_HOME 执行 `make finish`。这个命令实际重新进入综合和原生详细布局，覆盖了输入候选。

证据来自 state `var/overnight/gcd-20261014/`：

| 项目 | 实际证据 |
|---|---|
| DPL 候选 SHA-256 | `5b0a85e71d538b10697c2ce01d4ce10a113d95e050804afc09f5f9351798d3b9` |
| handoff 中记录的 SHA-256 | 同上；候选原文件当前仍与记录一致 |
| 下游 `3_5_place_dp.odb` / `3_place.odb` | `64ac1b1e6dd3ff491bc2a32edf016f6a3ba036968cfc9db60ce1408dee6bc7c1`，与 Flow 原结果完全相同 |
| 下游 `4_cts.odb` / `5_route.odb` / `6_final.odb` | 各自与 Flow 对应文件逐字节相同 |
| EF 任务 | `run-cab338b6e19b4c1e8b5854e721f3189d`，任务确实 succeeded |
| 实际任务日志 | 执行 `synth_canonicalize.tcl`、`Running detail_place.tcl, stage 3_5_place_dp`，再复制新的 `3_5_place_dp.odb` 为 `3_place.odb` |

交接记录：`handoffs/dpl-routed-r3/handoff.json`；物理结果：`handoffs/dpl-routed-r3/results/asap7/gcd/base/`；日志：`tasks/dpl-routed-r3-finish/*.zip` 的 `stdout.log`。DPL 原实际测量为 candidate HPWL 694.4µm、framework 696.7µm，候选本身存在，但收益没有被这个下游执行保留。

所以目前可以确认四项目均被调用且完成各自实验，但不能确认四专业能力已形成保留 DPL 作用的完整接力。此前我仅依据提交、文件存在及后续运行成功判定接力通过，验收遗漏了消费起点和重跑覆盖。该错误位于交接适配/阶段调用及验收，不是 DPL 原算法无效，也不是 EF 没有执行命令。

## 两条链路必须分别汇报

| 链路 | 真实状态 |
|---|---|
| Flow → DPL → CTS/route → Goal → ECO | DPL 作用被后续重跑覆盖；Flow 选中利用率22%导致显著占地代价；Goal 四源码候选因36–37个DRV被拒；ECO未找到有益动作。整体协同收益未通过 |
| 原 ORFS → 独立 ECO → 功耗回收 → Query/Codex 定点动作 | O2 已验证：共同 FF/310ps 下 setup闭合、功耗−0.1583%、单元面积−0.3846%、core/die不变；独立重放、与原 ORFS/ECO 的逻辑等价通过 |

O2 不是所有专业 Agent 的联合收益。`u158` 是这份 GCD 的具体诊断结果，不应成为通用设计规则。

## 单机底座真实能力

本次通过公共 API 查到507个GCD运行：470 succeeded、31 failed、6 cancelled；已索引149个快照，最新O2事实可正常查询。这些是任务/快照计数，不是507个独立优化候选。

EF 已统一任务、并发/资源、日志、取消、运行身份和原始产物；DF 已统一design/revision/run/snapshot、对象/关系、指标、来源、部分时序事实。历史并发读锁故障已修；DF11快照重启前后逐值一致。任务监控和事实查询具备本机可用证据。

仍不能把整个平台称为单机业务成熟：物理交接语义保真未通过、专业输出并非全部自动导入、推理上下文入口不完整、关键用例仍依赖root脚本，尚未证明时间/token净收益。EF执行成功与DF事实可查不保证上游修改真的被后续阶段消费。让EF核心承包EDA决策并不能解决这些问题，应由薄领域适配负责。

## 评价方式

目前已有固定条件测量、DRC/布局/电气检查、控制实验、空目录重放、O2逻辑等价和工程回归；整体单项/组合及数据增强效率评测还未完成。

参考 [PDAgent-Bench v2](https://arxiv.org/html/2606.17253v2) 的任务与闭环工作流双层评价，以及报告理解、归因、脚本执行和最终PPA的区分。该文包含商业EDA任务，不能把其用例与当前OpenROAD平台直接等同。借用评价方法，无需照搬其API多Agent框架。

本机首先需要一份小型固定验收集：同一设计/工具/库/约束/预算下，ORFS基准、各专业单项、有关组合及Codex动态协同；正确性/硬约束先于PPA收益；分别量化执行准备、工具计算、归档/入库和模型推理时间，保留失败成本。数据增强对照固定Codex模型及任务，比较原始报告方式和统一事实方式的完成质量、token、工具调用、人工介入及耗时。构建和一次性环境准备与日常重复成本分别列出。

这是验收数据和脚本，不是第三个评测底座。Codex做业务判断，确定性工具给事实。

## 建议的修正顺序与阶段交付

1. **交接保真优先。** 改DPL→CTS适配，从声明的placement起点执行明确后续stage，验证不会重新综合/布局覆盖。记录下游起点实际hash/对象状态，保持后续stage合法改变的记录；用不加DPL的匹配控制测其最终PPA作用。通过后再重算完整链路验收。
2. **统一目标及选择。** 将目标时钟、评价角、功耗/单元与core/die面积边界随任务传入；保留专业原评分，但由Codex按共同条件判断接力、分支或保留旧最好结果。验收为失败/退化的候选不自动成为唯一后继。
3. **简化单机业务入口。** 从准备器移出gcd/asap7/目录固定项，由已有profile/设计输入绑定决定；自动组织导出/入库，向专业推理接收点交付简洁诊断上下文。Agent只需指定设计、目标、能力与预算。验收为GCD及第二个设计都无需改源码/手写环境与物理拼接。
4. **单项与组合对照。** 先在共同环境证明平台包装不改变各原生能力，再比较有关单项/组合及动态工作流。要求平台保留同条件最佳合法结果；是否超越最佳单项用实际对照证明，不将百分比机械相加。
5. **测量并减轻底座成本。** 根据实测去掉重复身份扫描、无必要的数据往返/打包，复用不变输入；记录Query帮助的正确率和成本。没有净效率证据时，不声称省token或加速。
