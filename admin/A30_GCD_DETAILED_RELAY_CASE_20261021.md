# GCD：专业接力实际做了什么、为什么有效

本案例采用已完成的 ASAP7 FF / 310 ps 实验，保留全部成功和拒绝分支。数字来自每棒完成详细布线/RCX后的共同测量；原生布局 HPWL、原生估计时序和最终物理 PPA 分开解释。

## 2. Flow 提供了什么，为什么还需要下一棒

Flow 调整的是流程配置和参数，不修改 OpenROAD 优化源码。F37 在完整原生搜索后已显著降低功耗，但面积 44.8918 超过原上限 42.6757 µm²。Codex/Query 将它识别为“有潜力、未满足最终约束”的中间态，而不是简单当作最终成功或直接丢弃。

后续专业接到的是实际检查点、设计事实和冻结目标。平台保存 Flow 产物，并让 DPL 取合适的 `3_4_place_resized.odb`；取样原件与 DPL 输入已有字节核验。Goal 接到当前设计状态，继续优化其单元/连接/物理状态。

## 3. Query 和 Goal 如何处理功耗与时序冲突

Goal 的原生阶段证据表明，功耗回收可能带来 setup 时序债务，后面的布局和布线也会改变时序。Query/Teacher 据此把问题具体化为：在已经闭合时序的早期功耗回收入口，防止某些回收动作再次破坏 setup 闭合。不是无依据地另造一个“归因框架”。

Student02 实际修改 `src/rsz/src/policy/RepairPowerPolicy.cc` 的 `withinPhaseBudget`：在原 `early_forced_reclaim` 阶段，若入口 TNS=0 且 WNS≥0，尝试后的状态也必须保持 TNS=0 且 WNS≥0；否则拒绝并回滚。这个判定同时覆盖原单动作 journal 和窗口 journal 的提交路径，并保留原预算限制。

实际记录为 **316 次检查、186 次拒绝、186 次对应回滚**，说明机制确实触发。记录中的 `early_closure_budget_tns_after_ns = −25.34079` 是试探信号的汇总，不能当作最终采用状态的 TNS。原生估计与最终 DRT/RCX 也不能混成一列。

除阶段记录外，已有一次同配方源码对照：声明的 701 个源码文件中，仅该策略文件不同；工具链/CMake相同，Tcl 除输出目录外相同。未修改源码对照为 0.7673536893 mW、setup TNS −0.890416 ns；G02 为 0.71564863902 mW、TNS 0，即功耗再低 **6.7381%**、面积增加 **0.3365%** 并恢复时序闭合。这支持该具体源码增量的作用，但只是一次开发对照，不是跨设计统计因果结论。

F37→G02 的实际最终增量为功耗 **−19.6723%**、实例面积 **−12.8614%**。G02 相对 B0 功耗 −47.898%、面积 −8.3364%，其中包含 Flow 综合/方法来源与后续优化的累计变化，不能把全差值归给某一个 Agent。

## 4. DPL 为什么有局部收益，却没有直接成为最终最佳

DPL 优化详细布局源码，其原生目标是合法最终 pin HPWL。原一轮三 Student 和 Teacher 已完成：Diamond 参考 HPWL 536.9 µm，原生选中 Student02 为 527.6 µm，降低 1.7322%；日志还记录了 frontier 候选、精确接受和回滚等实际动作。

但原生选中的 D02 经 CTS/详细布线后，实例面积仍为 44.6148 µm²，超过原约束。因此原生 HPWL 改善不能直接写成最终 PPA 成功。Student01 的 D01 是另一实际候选，原生 HPWL 530.9 µm；它交给 Goal 后形成 DG1。不能把 Student02 的 HPWL 或动作计数算到 Student01 祖先上。

D01→DG1 功耗降低 **12.6104%**、实例面积降低 **11.9286%**，恢复为合法结果。交接核验保留了 D01 的实际设计单元/连接和约束；Goal 会去掉 filler 与信号布线，执行自己的优化再布线，**不会自动把 DPL 学到的 C++ 合并进 Goal 的 C++**。这是设计状态的专业接力。

DG1 没有超过 G02 的最低功耗，所以 Codex 保留 G02，同时归档 DG1。不同分支的阶段/配方有差异，G02 与 DG1 的差值不能单独解释为 DPL 的因果收益。

## 5. ECO 做了什么，为什么没有采用

ECO 实际消费存在时序问题的 G03，而不是在已闭合的 G02 上做无事可做的展示。原生八轮后，setup TNS 绝对债务约减少 **69.1%**，最差余量也改善；但没有达到 TNS 0，且原生详细布线计数仍有 54 处违反。补全布线后 DRC 归零，时序仍未闭合。

因此该支路是一次真实但未达到业务约束的修复，保留其动作、指标、路由变化及拒绝理由。不能把 GE8/GEC 写成已采用结果，也不能拼接到 G02 的祖先链上。

## 6. 平台在这条链里的具体作用

- **执行底座 EF**：统一承接构建、布局、CTS、布线、提取和证明任务，保留实际运行与产物身份。
- **DF/DI/Query**：提供同条件事实、路径与参数/源码/阶段证据，形成后续专业可消费的上下文。
- **Codex**：选择值得接力的中间态，比较局部与最终收益，拒绝不合格分支，保留最佳合法结果。

G02 和 DG1 都已有全 18 输出 ABC-PDR 与独立 DRT/RCX 七值同值证明。这里能够支持“平台真实集成不同专业，并形成合法接力收益”，但不能声称所有专业每棒都改善、四专业串行联合最优或已超过最佳单专业的普遍上界。
