# 正式实验前协同优化审计（2026-10-16）

审计基线：根 `26423ac`；本轮不修改生产代码、部署、专业算法或既有评测工作。证据目录：`var/business/preformal-audit-20261016/`。修正切片及拟议契约见 [施工计划](PREFORMAL_FIX_AND_EXPERIMENT_PLAN_20261016.md)，尚未实施。

## 业务结论

两个核心实验应分别证明：**同等机会与预算下协同优化的最终 PPA 有价值**，以及**同一个成熟 Agent 使用平台后能更可靠、更省事地完成同一任务**。

当前已经具有本机实验、事实回流和部分真实接力能力，但尚未满足正式实验的全部准备条件。不能用“所有项目都调用成功”代替“团队强于单项”，也不能用“接口更多”代替“Agent 工作更简单”。优先修的是具体的结果交付和一致性接点，不需要再造调度大框架或评测底座。

本次新增复现两项：**没有验证回执仍可采用**、**并发采用较差结果可覆盖较好结果**。另外确认默认 Flow 返回值、默认来源模式、任务等待和数据交付仍有会误导或拖住主 Agent 的缺口。

## 本轮新增问题及证据

### F1：采用不绑定验证回执——正式实验阻断项

`chip_evolve/selection.py:41` 的 `select` 读取指标、约束及本地 incumbent，直接写采用结果；`cli.py:319` 也没有要求传入验证回执。已有 `validate` 能证明与重放，但它和 `select` 是两个独立入口。

临时目录复制一份真实测量，目录内没有任何 `validation.json`，调用原函数仍返回 `adopted=true`。这证明“先验证后采用”目前依赖调用者纪律，尚未形成可核验的采用边界；不表示历史已采用结果未经验证。A11 GCD、A9 AES 已有的证明和重放事实保持。

证据：`adoption-reproduction.json` 的 `unverified_adoption`。复现未写任何生产结果。

### F2：并发采用会丢失较好结果——正式实验阻断项

`selection.py:44` 的指针读改写没有设计范围锁，`config.py:18` 直接写 JSON。两项决策可以读到同一旧 incumbent，各自判断可采用，后完成的较差候选覆盖先完成的较好候选。

临时目录中用受控线程交错复现：旧功耗 1.0 mW，两个候选 0.8／0.9 mW，其他指标相同且均满足真实原目标；两者均被接受，最终指针为较差的 `audit-worse`。这是当前代码的确定性交错复现，尚未发现生产中同样事故。

修正应限于采用事务：同设计、同修订、同目标／条件锁内重读当前值，核对回执并原子发布决定。专业实验仍可并发，不能用全平台串行解决这个小接点。

### F3：Flow 代表输出容易被误用——正式实验阻断项

`professional.py:405` 使用 `max(candidates, setup_tns)` 写顶层 `result.json`。它没有按全局可行性、功耗和面积选优，也没有明确给出“这只是代表项”的机器可读状态。

用本轮实际 AES 六候选重现：setup TNS 全为 0，返回第一份 **71.589611471 mW**；最低功耗为 **45.410703868 mW**，两者都超限。全部候选保存在 `candidates.json`，因此不是数据丢失，但只消费顶层路径的下游会继承偶然第一份。

修正不是在底座增加综合评分器，而是明确候选集、可行性和显式选源。Codex 判断取舍，不能将原生 winner、代表项与最终采用项混为一谈。

证据：`flow-representative-audit.json`。

### F4：默认来源与已认证来源不是同一条路

`cli.py:29` 默认 `--flow-recipe legacy`。A11 完整迁移通过的是显式 source 模式。正式实验若忘记这个开关，会回到保留的旧路径，而不是自动获得 A11 的来源继承修复。

source 资格也有明确边界：`flow_recipe.source_binding` 要求实际登记 ORFS 任务；不能从任意最终 ODB 反推完整 RTL／综合来源。正式实验应冻结已认证模式并在启动前显示所用资格，默认兼容路径不应被当作新实验的无条件推荐路径。

### F5：统一目录与采用状态仍有分散

EF 的 run／artifact 与 DF 的 design／snapshot 已统一；但是 `Deployment.state/designs/<design>/incumbent.json` 是每份本地 runtime 的指针。A11 GCD 和 A9 AES 分别位于不同 runtime，另有历史 A7 分支。

因此“新 runtime 没有 incumbent”不等于“该设计没有历史合法结果”。正式 campaign 必须明确带入冻结基准和保留分支；按设计、修订、目标和条件查到其出处。不同条件不强行合并为一个全局冠军。无须再建一套数据库。

还有一项语义边界：`physical.publish` 的快照 `revision_id` 使用实验名，`comparisons.compare` 核对 design_id／objective_id／condition_id，没有独立核对同一功能 RTL 修订。原始输入 hash 有留存，但目录上的 revision 目前不能直接被当作“同一 RTL 版本认证”。本次未发现历史实际比较混入不同 RTL；正式清单必须显式绑定 RTL／设计输入内容身份，不能只看同名 design。

### F6：等待与交付失败仍会打断简单用户流程

`Jobs.submit:129` 在非终态时每秒轮询，没有无 worker／不可调度／资源正常等待的区别。健康大任务不应强杀；但无人消费时也不应让主 Agent 无限等待、反复猜原因。

`Jobs.http:35` 对导入使用 60 秒同步请求；`physical.publish:456` 同步等 DF 入库。历史 `aes-native-canonical.log` 有 `TimeoutError`，`s6-gcd-yosys-validation.log` 有 `RemoteDisconnected`。后来正式恢复成功，计算未重复，但原业务命令仍因此失败过。

源码存在同步耗时导入和请求锁的接点，但仅凭这些记录不能认定断连的唯一根因。应先用实际部署版本和隔离大快照复现，区分读取、解压、解析、写库、等待、客户端超时与服务故障；复用已有导入回执和任务身份，避免简单无限重试。

### F7：Query 有证据不等于结论自动正确

A11 AES Query 曾把 ORFS reference 的 run ID 误称为 Goal incumbent，独立 SDK 核对和后续受限 Query 已纠正。现有 `diagnosis.py:186` 主要检查 scope、回答及证据非空，没有因此证明摘要中每个实体与引用都匹配。

任务交付应将 source、reference、candidate、retained result 的结构化身份和指标作为事实；模型负责解释。对影响派发／采用的身份做轻量一致性核对，不把它扩展为另一个通用 Agent harness。

## 现在各专业如何协同

实际方式是 **Codex 显式选择专业、来源和分支 → 根业务入口准备输入 → 专业保持原算法 → EF 执行 → 最终共同测量 → DF／SDK／Query 交事实 → Codex 选下一步**。尚无自动保证“四专业任意组合都更好”的机制，也不应以固定四步串行代替判断。

| 专业 | 改动对象 | 适用的交接含义 | 当前应避免的误解 |
|---|---|---|---|
| Flow／A2-ORFO | 综合、布局、CTS、布线配置与参数 | 可重建的完整来源、原阶段继承、多个候选 | 参数声明存在不等于工具消费；原生评分改善不等于最终可行 |
| DPLEvolve／ReviewDSE | 详细布局的 OpenROAD C++ 方法 | 绑定布局产物和源码／二进制，继续 CTS／route | 不是 RTL 优化；代码方法与某次设计 ODB 不是同一类交付 |
| GoalEvolve | resize、Vt、buffer、reroute 等 C++ 方法及原 recipe | 指定输入上执行其专业优化并形成新物理结果 | 与 ECO、后续时序修复可能重叠；不能假定任意已有源码都可用统一 replay 参数重放 |
| TimingECOAgent | 原有局部时序 ECO 动作 | 有可影响的真实路径／对象，再完整校准和测量 | reg2reg 报告不覆盖所有失败路径；零有效动作不算优化贡献 |

统一底座负责确定性物理工作，不替 Codex 造决策循环。专业内部的 checkpoint、候选筛选和 Teacher/Student 状态留在原项目；跨专业的事实、源身份和产物通过公共边界。

## GCD 做了什么，通用性到哪里

最新 A11 真正运行了完整 Flow、实际新布局的空接力、同输入 DPL 原框架和固定优化源码、共同测量、18 输出证明及独立重放。固定源码相对 Flow 输入功耗再降约 **0.700843%**、单元面积降 **0.811952%**；相对 DPL 框架功耗约降 **0.324646%**。

GCD 相对原 ORFS 的大幅差异主要来自来源／配置切换，不能全算团队优化。新分支功耗比历史 A7 更低，但面积更大，必须按冻结目标解释取舍。

同一来源继承／搜索／数据交付在 AES 也跑过，因此不是 `if design == gcd` 的补丁。**但当前业务装配不等于任意 PDK／多时钟设计通用**：Goal/ECO 准备仍明确使用 ASAP7 路径和模板；`clock.py` 要求一个物理时钟及匹配周期。两次设计实测证明了有限适用范围，正式新设计须先通过输入资格。

AES 最新六候选都未满足原业务上限；保留的 A9 DPL→Goal 结果相对 ORFS 功耗约降 **0.501602%**、面积约降 **0.129007%**，这是已有有限正例，不足以证明同预算团队优于最强单项。

## 为什么整体表现不够好

已知原因分四层，不能归咎于某一个 Agent 或全归于底座：

1. **起点与口径**：AES 默认内置综合明显优于完整 Yosys 来源的功耗／面积起点。按自身差基准改进仍可能输给 ORFS。原 TT/CP0 与最终 FF 目标不同。
2. **阶段交互**：较低 HPWL 不保证 RCX 后功耗低；布局／缓冲／尺寸／时序修复可产生真实取舍。Goal 接手重新布线也可能改变 DPL 的最终收益。这需要同输入的阶段控制，而非凭日志猜唯一原因。
3. **团队业务接点**：候选集到代表项、显式选源、跨 runtime incumbent、验证后采用和并发写入尚未全部收口，能误导决策或覆盖成果。
4. **运行成本**：导入／查询故障会浪费预算或中断，固定四专业运行会在无适用动作时增加无效工作。

修复 handoff 可恢复被集成吞掉的能力；它不自动创造算法上的互补。保留最佳合法分支可以保证交付不退步，但**“没有退步”只是保底，不能当作 1+1>2 的证据**。还需测量正向边际贡献及同预算相对最强单项的结果。

最终原约束必须满足，中间探索不必每一步都同时改善全部指标。A11 夜间接力按批准计划只从合法 Flow 来源启动，因此 AES 没有强行续接；后续可以明确预算运行“暂时超限→Goal 回收”的探索分支，但须标出来源和风险，不能直接采用中间结果。将所有超限中间态都禁止，会封死一部分可能的互补路径。

## 底座是否帮助 Codex、单机是否成熟

已帮助的具体事实：统一受监管执行、资源与 producer；真实断点恢复不重复 EDA；三类设计快照、候选对照、来源可查；原方法经 EF 与直接 EF 的匹配控制一致。

本次实况：EF worker 在线、idle，waiting/queued/retry_wait 都为 0；DF 可访问，474 份快照，约 28.98 GB 数据库。两次健康读取耗时不同，不能把单次延迟当作长期性能结论。健康页中可选 `evaluate.protected` evaluator 不可用，不等于当前 openroad-data 执行能力不可用，也不应因此新增评测底座。

成熟度判断：**单机核心路径可用，尚需人工核查部分交付与结果选择，未达到正式批量实验所需的少干预稳定性。** 目前能集中物理工作，但还没证明总体比裸 Codex 简单／省 token／省时间；本次列出的等待、默认值与多 runtime 指针正是应收口的复杂度。

## 已有评测证据和不足

项目并非完全没有评测：独立 `var/ablation-20261009/delivery/results.json` 已有 1152 条组件实验记录，本次只读，不改用户正在开发的 `admin/evaluation/`、DF、DI。

其中 GPT transport 的汇总：

| 条件 | 正确数／总数 | 可以说明什么 |
|---|---:|---|
| 完整接口 | 89/96 | 不是所有任务都正确 |
| 关闭关联查询 | 89/96 | 准确率相同；85 对双方正确且用量完整任务中，完整接口 token 少 45.27%、时间少 29.18% |
| 关闭批处理 | 91/96 | 完整接口不总提高准确率；87 对中的时间节省为 −3.54%，即完整接口略慢 |
| 关闭紧凑输出 | 92/96 | 精简存在准确率取舍；88 对中的 token 节省 10.35% 不能抵消未报告的错误 |
| 关闭原生补算 | 74/96 | 原生补算在这批任务中有明显的正确率价值 |

这些是限定任务及配对条件的描述性结果，不是全平台相对裸 Codex 的直接结论。样本选择、重复、缓存、初始化和用量缺失要保留。另一 transport 的 576 次尝试有 450 次 provider 请求失败，不能拿它直接评价模型推理能力或宣称完整组件效果。

因此应继承已有事实核对、配对成本和失败记账方式，围绕两个产品主张冻结正式协议，不另造大型 benchmark 产品。当前缺少的核心是：**团队 vs 单项的同预算最终 PPA**，以及**完整业务任务上的裸 Codex vs 平台能力**。

## 两个核心实验的方向

**实验一：PPA 与协同价值。** 固定设计修订、原业务目标、基础版本、输入库／单位／SDC、实际物理来源、模型与预算，比较 ORFS、各专业单项、适用的自适应协同。Flow／DPL／Goal／ECO 都获得相同的可用来源政策和预置方法，不给团队额外未记账历史赢家。综合来源变化单独列控制，避免把来源优势算成协同。

报告每个设计最终功耗、面积、时序、可行性、证明、DRC、运行成本和失败；团队需与最好单项同总预算比较。固定方法的单项／组合重放另作机制消融，不能冒充新源码搜索。至少扩展到 3–5 个合格真实设计，GCD 以工程回归为主，重复数与预算在小规模预实验后冻结。

**实验二：统一性、集成性和封装性。** 相同 Codex、专业能力和任务，比较直接使用原始工具／文件与调用平台；既要覆盖查询诊断，也要覆盖提交、监控、交付、取消、恢复、候选选源和交接。先看完成正确率、人工干预和证据完整性，再比较双方正确任务的总 token、时间、工具次数、读取量、重复 EDA 与失败恢复成本。初始化／预索引成本和热态成本分别报告。

PDAgent-Bench 可参考任务级与工作流级评估、错误分类、完整执行与 token 记录；它的知识／脚本题得分不能代替本平台的两项产品证据。参考：[论文 v2](https://arxiv.org/html/2606.17253v2)、[官方仓库](https://github.com/fenggev56/PDAGENT-BENCH)。本次查阅了这两份一手材料，没有复现其全套实验。
