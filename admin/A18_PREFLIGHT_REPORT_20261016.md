## 一、实际运行与来源决定

权威资产根为 `var/business/a18-preflight-20261016/`。`campaign-r2/campaign.json` 在分派前冻结两个设计、来源/原目标、A16 环境及四项预算。GCD 使用 A11 六个 Flow 候选中唯一满足原约束的来源；AES 改用同条件、同目标且已有完整验证的原 ORFS 起点。

第一次来源说明把 AES 现代完整来源错误称为“可行”。实际它违反原功耗、cell、core 和 die 上限，后续 DPL/Goal 又不能改变芯片轮廓。此次错误已纠正并保存到 `source-decision-correction.json`；原 `campaign.json`、第一次 GCD/AES 尝试和全部失败成本保留，未回写成成功、未放宽目标。r2 允许选择有完整验证的同条件原 ORFS/保留分支，不能强迫下游消费一个无法修复轮廓的起点。

每设计固定运行：DPL 原 framework 控制与已验证优化源码各 10,800 秒预算，Goal 原 baseline/p0 单项与接 DPL 各 7,200 秒预算。全部是原固定方法，不是新源码演化；已完成的 Flow 六候选用于本轮输入/查证，不重新搜索。**Goal p0 包含原时序修复流程，不能代表新的 Goal 功耗源码搜索，也不能冒充此前 Student4 的算法效果。**

GCD 四项 setup/hold TNS 都为零，core/die 均 57.9701/75.8293µm²。固定 DPL 相对所选 Flow 源功耗再降 0.700843%、cell 降 0.811952%；这个结果与 A11 已验证输出一致，本轮是重现和接点确认，**不是新增优化收益**。DPL→Goal 相对 Goal 单项功耗低 0.356653%，但相对 DPL 单项高 0.237979%，只多 0.1002ps setup 余量。不能把“优于 Goal 单项”写成“优于最强单项”。

AES 原 cell 上限为 1255.75µm²，1256.04 即使只超约 0.0231% 也没有放宽。其固定接力比 Goal p0 单项功耗低 0.121542%，仍不合法，且不如已验证的 A9 Goal 功耗/面积组合。AES core/die 保持原 1941.63/2321.51µm²，setup/hold 闭合；新分支未替换 A9。

作为历史产品结果，当前 GCD 相对原 ORFS 功耗 −59.450548%、cell −21.166760%；AES 保留分支相对原 ORFS 功耗 −0.501602%、cell −0.129007%。**GCD 的大部分差异来自来源/综合路线改变，AES 收益来自前轮；这些不能统称本轮协同增益。** GCD/AES 的剩余时序余量也单列，不能只报功耗。

八项结果和原约束差值见 `preflight-report.json`；它的 `execution_gate=passed` 只表示固定步骤执行交付完成，`formal_study_ready=false`。不要把计算成功、合法、已验证和已采用混为一个状态。

## 三、handoff、恢复与完整验证

`handoff-input.json`、`input-receipt.json` 绑定真实来源 run、文件 hash、目标、条件、Query 上下文与接点转换。Goal 明确移除 filler/信号布线，保留源 cell/连接，再做原优化和布线；不宣称最终 routed ODB 可以原封不动交给所有专业。没有重跑综合覆盖 DPL 的旧问题。

GCD Goal p0 的 `pre_repair`、`post_repair_design`、`post_repair_timing` 指标逐值相同：在已闭合的起点上这两步没有产生可观察修复收益；后续 placement/route 又改变了测量。它说明当前固定时序方法对低功耗任务的适用性有限，不能据此断言完整 Goal 搜索无效，也不能在缺少匹配“只转换/重布线”控制时把最终增耗严格归因于某一动作。两个起点均已闭合，ECO 本轮记录为无适用时序修复任务，不强跑空操作或记一份虚假收益，见 `eco-applicability.json`。

AES 首次固定 DPL 的专业计算已经完成，交付准备器却遍历了配置内所有设计，因无关 picorv32 模板缺失而失败。正式根实现现只绑定当前 design；修复后用原 key `resume` 完成交付。`aes-dpl-recovery-before.json`/`after.json` 核对原四项 native operation 的 run IDs 全部不变，未重启源码搜索或已完成专业计算；原失败尝试仍计入成本。

GCD 首次使用 EQY 对所选 Flow 中间结果证明时，111 个内部分区中 46 个未证明，不能接受为完整证明，原失败 EF run 保留。候选网表与此前 A11 完整验证的网表逐字节相同；另冻结只用于验证的 `runtime/gcd-validation-yosys.json`，使用此前既有 Yosys 完整输出证明后端与原 ORFS 功能参考，不改 Liberty、目标或接受规则。最终 **18/18 功能输出证明、独立 CTS/DRT/RCX 七 PPA 逐值一致、SDK 身份一致**，经 `select --validation` 正式登记本轮采用。

AES 不对不合法新分支做虚假采用；重新核对原 A9 Goal 的完整验证、匹配结果 hash 和三类 SDK scope 后，在本轮独立决定目录记录保留。原历史文件不修改。

## 五、候选查证成本：正结果与失败都保留

两个设计各六个已完成 Flow 候选；直接侧读同样已规范化的原结果 JSON，平台侧读 SDK 核实的紧凑事实。不是故意给直接侧一堆无法解析的原日志。两侧使用同一原生 Codex `gpt-6.1-sol`/medium、相同工具权限和每次 240 秒，三次重复，先后顺序交替。任务仅列出可行 run、每个拒绝项的全部原约束违例和逐 run 输入引用；不选 winner、不做因果或 EDA。

首轮指令没有明确排除 compact 内的 reference，直接侧六份答案正确、平台侧六份答案多列参考项，严格 oracle 判失败；六个目标候选的违例内容一致。首轮 12 份答案、用量和错误全部留在 `codex-pairs/`，不能把其较低成本写成有效收益。

修订协议在两侧明确列出相同六个 target run IDs、reference 仅作上下文；**不改输入事实、独立 oracle 或正确标准，不只重试失败侧**，完整运行另外 12 次。结果在 `codex-pairs-r2/`：双方 12/12 答案正确，用量完整，形成六对成本。

| 修订后六对合计 | 直接侧 | 平台侧 | 观察差异 |
|---|---:|---:|---:|
| 输入+输出 token | 603,705 | 231,947 | −61.5794% |
| episode 墙钟合计 | 188.295s | 157.725s | −16.2355% |
| 正确答案 | 6/6 | 6/6 | 相同 |

逐对时间改善中位数仅 5.14%，GCD 一对平台略慢，所以不承诺稳定加速。准备两份事实另需 8.401s；若在此次三次热态复用中只加一次准备成本，平台时间合计 166.126s，较直接侧少约 11.77%。这仍不含历史索引/导入建设成本，不是冷启动或全工作流速度。

两版协议全部 24 次已知 token 合计 1,743,376，直接侧 1,164,890、平台侧 578,486；全尝试直接侧正确 12/12、平台侧 6/12。首轮属于协议开发失败，不能并入修订后“全正确”而不说明，也不能删掉其成本。使用/缓存原记录完整，cached input 不重复相加。专业执行前置 Query 的其他成本与上述查证子任务分开，不把本表当整轮模型总用量。
